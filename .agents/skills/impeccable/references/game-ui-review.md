# 千星游戏 UI 评审

先确认目标界面、玩法状态、尺寸、版本和证据来源。没有渲染或操作证据时，结果标为静态建议，不写“已验证”。默认方法为项目适配／单上下文。

| 维度 | 观察问题 |
|---|---|
| 目标与层级 | 能否迅速识别当前目标、关键资源与下一步动作？HUD 是否遮挡玩法区域？ |
| 状态与反馈 | 可点击、禁用、冷却、选中是否可区分？资源消耗和成功/失败是否及时反馈？不能只靠颜色区分状态。 |
| 布局与输入 | 中文、长名称、最大资源数和空列表是否裁切？热区在实际尺寸是否可操作？按钮是否靠得过近或被覆盖？ |
| 视觉语言 | 色板、字号、图标和间距是否符合主题？装饰是否抢走危险提示或主操作的注意力？ |
| 节奏与动效 | 动画是否阻塞操作、分散注意力或掩盖结果？哪些意图可在千星实现，哪些需要降级？ |
| 跨状态与设备 | 开局、首次成功、失败、暂停/恢复、重开是否连贯？按当前阶段检查画布与真机安全区。 |
| 平台还原 | imageId、字体和控件属性是否已核实？区分占位、模拟器差异和真机缺陷。 |

只记录实际发现，每项写：

```text
目标/状态/尺寸：
方法与证据：项目适配／单上下文；来源、版本、截图或操作记录
问题与影响：可观察现象，以及阻碍了哪个玩家动作
处理：本轮修复、留待真机核验，或暂缓及理由
复核：相同状态与尺寸的结果；未执行时明确标注
```

实际操作与试玩继续遵守七步工作流的用例和 runtime 记录要求。HTML 的 DOM、网络加载和键盘焦点可用网页工具检查；Lua 控件的输入、生命周期、预算和平台行为使用相应阶段的知识库、模拟器与真机验证。
