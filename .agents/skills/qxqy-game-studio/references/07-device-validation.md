# 7. 真机试玩验证与 bug 修复

## 输入与适用时机

先按 [逐步验收](stage-approval.md) 核对步骤 6 的用户验收；未确认就停在测试交付。读取已验收候选、测试证据、资产清单和导出警告。以下为首次导入与后续 Lua 更新的标准流程。

## 首次交付：一个整合 GIA，Lua 为空

1. 核对正式存档的入口脚本 `path` 指向单文件产物、`source` 为空，UI/模板、映射和挂载完整，执行 `npm run check:saves`。旧内嵌源码先比较并合并有效内容回 `src`，不能直接丢弃。
2. 导出一个包含所需 UI/模板、脚本映射和挂载的 GIA 整合包，入口 Lua 仅为空白占位，不放生产代码。当前 Web 导出格式为 `gia-combined`（别名 `combined-gia` / `combined`）；按实际工具 schema 或页面入口操作，不编造 MCP 导出工具。
3. 检查导出警告、包中入口脚本数量/路径和空源码。交接说明写清 GIA 文件、挂载对象、需核对的控件/模板及测试版本。单独脚本 GIA 与整合包的挂载行为不同，不能笼统认定所有 GIA 都保留或都不保留挂载。
4. 用户把 GIA 导入游戏，打开千星沙箱，核对映射/挂载并找到导入后真实的入口 Lua 文件。真实路径由用户在游戏环境确认，不从示例、最近修改时间或账号目录猜选。
5. 用户将真实完整路径填写到 `lua.deploy.local.json`；可用 `npm run setup -- --target "真实路径.lua"` 辅助配置。
6. **配置后立即执行一次 `npm run deploy:lua`**，不等下一次编译。空白目标没有项目 UUID，归属校验会停止；读取目标，给出真实路径、检查结果与覆盖计划，取得用户对此文件的明确同意后执行 `npm run deploy:lua -- --overwrite`。普通部署授权不包含对此冲突的覆盖同意，不能自行补参数。不把“配置已保存”或“等待覆盖确认”当成部署成功。
7. 核对部署 SHA-256、源/目标和备份回执。用户在千星沙箱保存或重新加载并试玩，确认使用了本次版本。

本模板的 GIA 整合包映射/挂载说明依据已安装模拟器 0.4.1 的导出实现；当前项目的实际导入、真实路径、索引和加载行为必须由真机证据验证。没有真实目标时交付 GIA 与路径填写步骤，停在用户操作回传处，不伪造配置或部署结果。

## 本机目标配置

```json
{
  "targetFile": "C:/请替换为千星沙箱确认的真实目录/main.lua"
}
```

这必须是导入后核实的绝对 `.lua` 文件路径。JSON 使用反斜杠时须转义；示例不是已选目标。配置、`.lua-project-id`、备份和部署记录均不提交 Git，单独保存 JSON 不触发监听或复制。

setup 或首次构建生成稳定的本地 UUID，产物首行记录 UUID 与项目名。已有目标的首行标记缺失、无效或 UUID 不符一律停止，包括零字节、UTF-8 BOM、纯空白和旧版文件；即使历史哈希一致也不绕过。同 UUID 仍保护外部修改。先读取、比较并合并有效内容回源模块；只有冲突已审阅且用户明确同意覆盖该文件时，才用 `--overwrite`，并保留原始字节备份。可用 `npm run deploy:lua -- --dry-run` 查看双方标识和计划，此命令不完成部署。

## 后续每次编译都 deploy

真实目标配置后，日常统一运行：

```sh
npm run build:lua
```

`npm run build` 同义；两者将同次编译产物自动 deploy 到配置路径。`npm run preview` 包含编译，因此也会同步。部署或校验失败时命令失败，不能只报告本地编译完成；失败构建不能复制旧产物。显式 `deploy:lua` 也会先重新编译再复制。

**纯 Lua 修改不重新生成 GIA。** 包括规则、数值、Lua 创建的界面和代码内索引修正，都沿用同一文件路径及现有映射/挂载。只有需重新导入的 UI/模板/资源、映射或挂载结构发生变化，才重导 GIA；重新导入后再次核对真实路径与索引，必要时改 JSON 并立即 deploy。

生产维护源始终是 `src/**/*.lua`，只有单文件产物被复制。不上传模块目录、`.map.json`、本机配置或备份；不通过手改 `dist` 遗漏维护源。

## 导入后的索引校准

用户提供的千星编辑器实际索引是依据。按控件身份辨别模板索引、运行时控件 Id、脚本映射和 imageId，不全局替换所有同值数字：

1. 读取 `controlGuidChanges` 或用户回传。连续 A→B→C 解析到最终值；同一 batch 的重编号按同时映射处理。
2. 将有效索引修改合并回 `src` 中的常量、配置、调用和身份检查；不直接修改产物。无法判断或缺少内容的引用保留待处理。
3. 核对存档的真实控件索引、入口脚本路径和空 `source`；相关引用已处理或确认无引用后，才按最新 revision 确认对应变更账本。
4. 保存结构改动，编译（目标已配置时自动 deploy），重启模拟器回归受影响行为，再由用户真机试玩。仅修复 Lua 引用不重导 GIA。

工具操作按当前 schema；工程操作需要 handle，写入使用最新 revision。详见 [步骤 5](05-lua-implementation.md) 和 [Lua 发布说明](../../../../docs/lua-modules.md)。

## 真机反馈、修复与验收

交付清单说明导入包、真实 Lua 路径、首次部署回执、后续编译命令、真实索引、试玩操作与预期。每条记录区分磁盘复制、编辑器重新加载和真机结果；只有实际覆盖的目标行为可标通过，未覆盖项明确列出。

回传应包含环境、操作步骤、预期/实际、相关画面或日志与可复现性，标 `runtime=device`。字体、裁切、层级等可用 [Impeccable](../../impeccable/SKILL.md) 根据真机画面评审；截图不能代替输入和性能测试。

缺陷先留最小复现，区分 Lua、素材、布局与平台差异。按逐步验收规则回最早受影响阶段，保留未受影响确认；修复后重新编译部署并回归。未加载或未验证的版本不能写“真机通过”。

## 产物与完成条件

交付空脚本 GIA、完整存档及源工程、实际索引/映射/挂载说明、真实路径的本机配置、首次及后续部署记录、测试结果和未完成项。没有真实路径、部署失败、未重新加载或缺少真机反馈时分别记录，不能互相替代。

目标覆盖且缺陷闭环后，提交实际验证范围、交付结果和剩余问题，标记 `awaiting-user-confirmation` 并结束本轮；用户明确验收步骤 7 后才标本轮完成。
