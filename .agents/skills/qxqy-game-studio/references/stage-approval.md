# 七步强制顺序与用户验收

七步是游戏开发的必经顺序。当前步骤的产物、自检与用户验收都完成后，才进入下一步；不能跨步、合并验收或提前制作后续阶段产物。此规则约束阶段切换，阶段内的必要修复和自检继续自主完成。

## 每一步如何结束

1. 按本步文档完成产物与自检；有缺项就继续本步，无法完成时如实交付已完成部分与缺项。
2. 展示用户可以审阅的产物、查看或操作方式、主要结果和已知限制。HTML 必须提供可打开的演示与操作说明，不能只展示代码或说“已生成”。
3. 在 `docs/production-plan.md` 记当前步骤、状态 `awaiting-user-confirmation`、待验收产物路径/版本与待处理意见。实际试玩另按 runtime 记入 `records/playtest.md`。
4. 请求用户验收当前步骤并结束本轮。异步问题只发出但尚未收到答复时也必须等待，不以继续独立工作为由预做下一阶段。
5. 收到用户明确认可当前产物并允许推进的回复，记录原话或可定位的消息引用、对应产物与确认范围，将本步改为 `accepted`，只进入紧邻的下一步。下一步仍有自己的验收点。

| 当前步骤 | 提交用户验收的内容 | 获确认后进入 |
|---|---|---|
| 1 策划 | 核心循环、输入、胜负、P0、风险与待定规则 | 2 用例 |
| 2 用例 | 规则覆盖、操作与预期、边界及人工验证项 | 3 HTML |
| 3 HTML | 可试玩演示、关键状态、操作/节奏、不可移植项 | 4 美术 |
| 4 美术 | 参考与样本、素材清单、色板/布局、千星还原方案 | 5 Lua |
| 5 Lua | 实现候选、构建与必要自检、存档/挂载、已知限制 | 6 测试 |
| 6 测试 | 用例与画面证据、缺陷回归、未通过项、模拟器候选 | 7 真机 |
| 7 真机 | 空脚本 GIA 导入、真实路径与首次 deploy、实际反馈/修复和剩余问题 | 用户验收后完成本轮 |

## 什么算确认

- 用户在看到本步产物后，明确回复“本步通过，继续下一步”“这个版本可以，进入素材阶段”等，可视为对当前版本的验收。“继续”只有在上下文明确指向正在等待验收的本步产物时才有效。
- “开始设计”“帮我做完整游戏”等总体任务、展示前的授权、工具绿灯、AI 自评、用户沉默和经过一段时间，均不等于逐步验收。提问、评价不明或提出修改时，不自行判断通过。
- 只收到修改意见时保持当前步骤。修改后重新展示产物并等待验收；不能一边修改 HTML，一边开始正式素材、Lua 或存档搭建。
- 不替用户填写确认记录，不将设计工具的评审分数写成用户意见。用户明确改变阶段顺序或逐步验收要求时，记录其新指令及适用范围；不能从普通“继续开发”自行推导例外。

## 恢复与回退

恢复时先对照实际产物和用户验收记录。`awaiting-user-confirmation` 且没有后续有效回复时继续等待，自动续跑、换会话或上下文压缩不改变这个状态。缺少可核实确认记录的最早阶段保持未验收，后续文件存在或代码能运行都不能补成确认。

已验收且未受变更影响的阶段保留原记录，按顺序核对即可。变更影响已验收的玩法、体验或还原方案时，回到最早受影响阶段，重新交付和验收后再按顺序核对、推进；不得借“窄修复”跳过尚未验收阶段。

模板工具/说明维护本身不属于游戏七步验收，不将本次文档改动当成游戏阶段完成，也不因维护模板启动游戏后续阶段。
