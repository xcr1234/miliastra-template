# Lua 模块、构建与单文件发布

开发时维护 `src/**/*.lua`，编译时打包为一个可读 Lua 文件。首次通过含空白 Lua 的 GIA 建立游戏内映射；用户填写真实目标路径后立即 deploy，此后每次编译自动 deploy 到同一路径。这里的编译是源码打包，不是字节码编译。

## 构建

`lua.project.json` 定义源目录、入口模块和产物；默认 `src`、`main`、`dist/main.lua`。日常入口为 `npm run build:lua`（`npm run build` 同义）：未配置 `lua.deploy.local.json` 时只打包到项目内；配置后自动把同一次编译的产物 deploy 到真实目标，复制或校验失败时整个命令失败。

```lua
-- src/game/score.lua
local M = {}
local value = 0
function M.add(points) value = value + points end
function M.get() return value end
return M
```

入口通过 `local score = require("game.score")` 使用模块。保留 `OnStart`、`OnUpdate`、`OnDestroy` 等已核验的平台回调，把实现委托给模块。模板的回调为空，不包含具体玩法。

- 模块名相对源目录，`game.score` 对应 `game/score.lua`，不隐式解析 `init.lua`。
- 支持未转义的单/双引号常量 `require("game.score")` 或 `require "game.score"`；每段以英文字母/下划线开头，后续可含数字。
- 不支持动态路径、别名或重定义/遮蔽 `require`。不使用绝对路径、`../` 或通过环境表访问宿主加载器。
- 每个模块有独立函数作用域，按需初始化，在单个脚本实例内缓存。建议返回 table；未返回值按 true 缓存，false 也只初始化一次。
- 只打包入口可达模块；缺失依赖、循环引用、路径逃逸、语法错误会在构建时失败。
- 产物自带局部模块加载函数，不依赖宿主 `require`、`package`、`load`、`loadfile`、`dofile`。`fengari@0.1.5` 仅在构建/测试时检查 Lua 5.3 语法和基本运行行为。
- 保留可读源码、模块注释与 `main.lua.map.json`。报错行落在某模块 `startLine..endLine` 内时，源行号为 `报错行 - startLine + 1`。

`tools/bundle-lua.mjs` 是内部打包实现，供工具测试和语法探针使用；日常编译统一走上述项目入口，不绕过已配置目标的自动部署。

## 项目标识与覆盖校验

首次 `npm run setup` 或项目构建会生成随机 UUID，保存到 Git 忽略的 `.lua-project-id`；重复 setup、构建和项目改名均复用该值。产物第一行是可读 Lua 注释，项目名称取自 `lua.project.json.name`（未设置时取目录名）：

```lua
-- miliastra-project: {"id":"fc296edd-4314-47ae-87dd-8705f80f11f0","name":"my-game"}
```

以 UUID 判定归属，名称用于核对。部署到已有目标前先读取首行：标记缺失、无效或 UUID 不符都会停止，空白文件与旧版产物也包含在内，历史哈希不能绕过此检查。UUID 相同仍检查目标是否被外部修改；需要覆盖时先审阅并取得用户对该文件的明确同意，再使用 `--overwrite`。Agent 不能把普通编译/部署授权当成冲突覆盖同意，也不能自行改写标记来通过检查。

不要在日常清理中删除 `.lua-project-id`；内容损坏会报错，不会静默重建。整体移动原项目时保留该文件；从模板创建独立游戏时不要复制它。新 clone 会获得新 UUID，因此部署到旧目标前需再次核对并同意覆盖。UUID、目标配置、部署记录与备份均不提交 Git。

## 编译日期与初始化日志

每次构建将构建机器的本地系统时间写入产物头部、行号映射的 `builtAt` 字段及构建终端，格式为 `2026-10-21 23:00:00.000 +08:00`。时区跟随系统配置，不强制使用 UTC 或北京时间；时间代表构建时刻，不是游戏启动时刻。

`lua.project.json` 的 `lua.startupLog` 控制运行时日志，省略时默认开启；必须使用布尔值：

```json
{
  "name": "my-game",
  "lua": {
    "root": "src",
    "entry": "main",
    "out": "dist/main.lua",
    "startupLog": true
  }
}
```

开启时，构建器在加载入口后包装已有的 `OnStart` 回调，先打印编译日期及初始化开始日志，原回调正常返回后打印完成日志。原回调的参数、返回值和错误继续传递；初始化失败不会打印完成日志。没有 `OnStart` 的纯模块产物不会新增生命周期回调，也不会打印这些日志。

将 `startupLog` 改为 `false` 后重新编译，即可关闭这些运行时日志；不会关闭游戏源码自己调用的 `print`，编译日期仍保留在产物头部和构建终端。目标已配置时，这次日志设置修改也会同步到游戏文件：

```sh
npm run build:lua
```

日志使用官方《[客户端控件API文档](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhtakr07vej4)》的 `print(...)` 普通级别日志接口；在千星编辑器日志中勾选“客户端脚本”查看。资料依据为知识库 2026-09-25 快照。

构建时间变化会使产物内容和 SHA-256 变化，即使模块源码未改。每次正常编译在配置目标后执行部署；仅当包括编译时间在内的完整内容相同时才跳过重复写入。自动部署直接使用本次编译结果，不为复制再编译一次。

## 首次交付：空白 Lua 的 GIA 与真实路径

1. 到步骤 7 且步骤 6 已获用户验收后，导出一个 GIA 整合包（当前 Web 的 `gia-combined` / `combined-gia`）。包内保留需要的 UI/模板、脚本映射与挂载，入口 Lua 的 `source` 为空，不携带生产 Lua 源码。导出前核对脚本路径、空 `source` 和导出警告。
2. 用户将 GIA 导入游戏并打开千星沙箱，核对入口脚本映射/挂载和真实索引，在游戏中定位导入后实际 Lua 文件。不能根据账号、关卡或示例目录猜路径。
3. 将该完整路径填写到 Git 忽略的 `lua.deploy.local.json`：

```json
{
  "targetFile": "C:/path/to/default_import_file/workspace/my-game/main.lua"
}
```

4. **填写后立即发起一次部署**；不要等到下一次改代码：

```sh
npm run deploy:lua
```

空白文件没有首行项目标记，命令会停止。检查提示中的完整目标路径和实际文件，取得用户明确同意后，执行以下命令完成首次写入并保留空白文件备份：

```sh
npm run deploy:lua -- --overwrite
```

不能自行添加覆盖参数。首次写入后，目标带有本项目 UUID，后续正常编译可按已授权路径自动同步。

可用 `npm run setup -- --target "真实完整路径.lua"` 代替手工写 JSON，但保存配置仍不自动复制；保存后紧接着执行上面的命令。目标必须是用户从千星沙箱核实的绝对 `.lua` 路径，可以包含中文和空格，文件名可与项目内产物不同。Windows JSON 推荐用 `/`，使用反斜杠时需写成 `\\`。

GIA 整合包的映射/挂载支持与单独导出脚本 GIA 的行为不同；实际导入后仍核对是否保留。这里依据本项目安装的模拟器 0.4.1 导出实现，不冒充该游戏的真机导入证据。

## 后续编译与部署

```sh
npm run build:lua   # 编译；已有真实目标配置时自动 deploy
```

每次只改 `src` 下 Lua、数值、Lua 创建的界面或代码内索引，沿用现有映射和路径，**不重新生成 GIA**。只有需重新导入的 UI/模板/资源、脚本映射或挂载结构变更时才重导 GIA；导入后再次核对真实路径和索引，必要时更新本机 JSON 并立即 deploy。

`npm run deploy:lua -- --dry-run` 先构建，输出源、目标、SHA-256、双方项目标识、归属校验状态、预计新增/替换/不变及是否需要确认；不会写入目标、备份或发布记录。无目标文件时允许新建；任何已有文件都先校验归属。

`npm run deploy:lua` 每次重新构建，构建失败便停止；成功后复制单个 Lua。相同内容不重写。替换前在项目 `.lua-deploy-backups/` 备份旧文件，先写临时文件再替换，最后核对目标哈希并记入 `.lua-deploy-state.json`。

导入后的零字节、UTF-8 BOM 或纯空白 Lua 同样需要一次覆盖同意；已有非空未知代码、归属不符或外部修改默认停止。先比较并将有效修改合并回 `src`，取得覆盖同意后才使用 `--overwrite`，替换时备份原始字节。自动编译部署遇到冲突同样报错，不把“本地打包成功”当作部署成功。发布记录按项目 UUID 关联哈希，备份与本机配置均被 Git 忽略。

## 模拟器与编辑器

Git 中的模拟器存档只保存 UI、索引和脚本挂载：脚本 `path` 指向 `dist/main.lua`（自定义时与 `lua.project.json` 的 `lua.out` 一致），`source` 留空。模拟器启动试玩时读取工作区路径；非空内嵌源码会优先执行，所以不把打包结果写进受 Git 管理的存档。`src/` 是维护源，`dist/` 已被忽略，构建日期与代码变化不会再造成存档差异。

`npm run preview` 自动先编译并运行 `npm run check:saves`；真实目标已配置时，这次编译也会 deploy。检查器只读扫描 Git 已跟踪和未忽略的新建 `*.save.json`，核验格式、空源码、产物路径和非空磁盘文件，有问题则返回失败。空模板无存档时通过，不创建占位工程或挂载。

迁移旧存档或遇到编辑器写回源码时，先比较内嵌内容与源模块/产物，将有效改动合并回 `src/`，重新构建和验证后再将 `source` 设为空字符串并保存。检查器不会自动删除任何源码。修改 Lua 后重新构建，再停止并重新启动试玩；修改 UI 或挂载后显式保存存档。

分享可独立运行的工程时，另带本次构建的单文件产物并保留相对目录。存档本身不再自带 Lua。本机路径/配置和备份不提交 Git；可携带源码的独立导出包放在忽略目录或通过发布附件交付。发布命令不修改模拟器存档，也不创建脚本挂载关系。

千星编辑器只映射并挂载目标单文件，不分别映射开发模块或上传 `.map.json`。后续编译更新同一路径，编辑器保存/重新加载后试玩。复制成功、模拟器通过与真机通过分别记录，不能把 deploy 回执当成游戏已加载新代码。

官方《[客户端控件和客户端脚本](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhbgxf0nynww)》说明只有建立映射的 Lua 才会上传；也提供多脚本调用机制。本模板选择单文件发布以简化映射，这是工程约定。知识库依据为 2026-09-25 快照；模板本身不包含任何游戏的真机验证结论。
